# 任务取消与归档记录

状态：已实现。核对日期：2026-11-16。

## 操作入口

- 任务名称打开共用右侧详情抽屉；未结束任务提供「取消任务…」。填写原因、核对受影响任务并确认后才取消。
- 活动任务的「交付记录」提供请求停止和查看运行入口。取消面板也列出全部受影响的活动或不确定运行。
- 已完成或已取消任务提供「归档任务…」。归档只收起日常任务列表和看板中的记录，不改变完成/取消结果。
- 「工作 → 归档记录」可搜索归档任务、查看说明、取消原因、计划和原始交付证据，以及恢复任务。
- 「项目」中的已归档项目提供「查看历史任务」。历史页可直接只读查看该项目全部任务，无需恢复项目；相关任务、计划、验收与运行详情保留只读访问。
- 即使所有项目都已归档，归档记录页和归档项目的任务/运行深链接仍可打开。

## 停止与取消的规则

停止操作对象是 Run，不是 Task。请求停止不等于终止外部进程；Agent 应停止写入并按协议确认，或由人类确认旧执行确实已经停止。确认之前保留锁，`RUNNING`、`STOP_REQUESTED`、`QUARANTINED` 都会阻止取消。确认后保留已有文件和执行证据，不回滚文件。

取消使用现有 `CANCELLED` 状态：

- 取消需求：取消需求及其未完成子任务；已完成工作保持 `DONE`。相关计划和未完成验收置为 `SUPERSEDED`，不能继续批准、领取或修订这项已取消需求。
- 取消工作：同时取消依赖它的未完成后续任务，按依赖图计算传递影响。其他独立工作不受影响。所属需求进入 `BLOCKED / TASK_CANCELLED`，需通过现有计划修订流程重排工作；不会把取消的工作算成通过验收。
- 取消 Bug：保留 Bug 和回执，禁止再次领取修复。
- 已完成、已取消或归档项目中的任务不能再次取消。没有直接重开已取消任务的操作。

取消预览包含目标任务版本、将取消的任务清单、相关运行和 `impactHash`。提交在同一事务中重新计算范围并检查版本、影响哈希、运行状态。SSE 更新改变范围后，面板保留原因，要求重新核对，并重置确认勾选。不能静默扩大用户已确认的范围。

## 归档与恢复的规则

仅允许归档 `DONE` / `CANCELLED` 任务，且相关任务没有活动或不确定运行。归档不是新的 Task 状态，也不删除任务、事件或证据。

归档需求时，同时归档尚未归档的已结束子任务，包括旧计划的历史子任务。每批记录保存 `archiveBatchId`，用于恢复该需求时仅恢复这批子任务；原先单独归档的子任务继续归档。所属需求仍归档时，应先恢复需求，再单独恢复子任务。

恢复只恢复可见性，不会重开、重试或重新执行。归档项目中的记录只读，必须先通过项目管理恢复项目，才能修改任务归档状态。

日常任务 HTTP 列表默认 `archive=active`，看板同样排除归档记录。按 `parentId` / `planId` 读取证据关系时默认 `all`，避免历史子任务从计划或需求详情中丢失。归档页使用独立的、按项目分页的历史查询，包含需求、工作和 Bug。现有记录没有 `archivedAt` 字段时按未归档处理，无需重写旧数据。

## 接口

- `GET /api/v1/tasks/:id/cancellation?projectId=...`：读取当前取消影响，返回 `task`、`source`、`tasks`、`runs`、`enabled`、`reason`、`impactHash`。
- `POST /api/v1/tasks/:id/cancel?projectId=...`：提交 `{version, impactHash, reason}`。
- `POST /api/v1/tasks/:id/archive?projectId=...`：提交 `{version, archived: true|false}`。
- `GET /api/v1/tasks/history?projectId=...&archive=only|all|active&q=...&cursor=...&limit=...`：按项目查询记录。活动项目的归档页使用 `only`，归档项目使用 `all`。

这些接口只向人类网页会话开放。任务和运行命令按传入项目检查归属；Agent 的领取、停止确认和回执继续走现有身份绑定协议。

## 结构守门记录

### 三问体检

- 真问题：用户无法明确放弃某项工作，也无法在不恢复项目的情况下查看归档项目中的历史任务。
- 更简方案：复用 `CANCELLED`、现有 Run 停止确认与共用详情抽屉；归档用可选字段，不增加任务状态、归档表或通用状态修改接口。
- 会破坏什么：取消会影响依赖、需求汇总、批准和最终验收；归档会影响列表过滤、详情跳转与项目选择，必须保留证据可达性。

### 数据结构定稿

- 核心实体仍为 Task、Plan、Run 和 Acceptance；需求包含子任务，工作间有依赖图。
- Task 增加 `cancellation: {at, reason, rootTaskId}`、`archivedAt`、`archiveBatchId`。可选字段兼容旧 JSON 记录。
- 所有取消、归档和恢复由人类命令在存储事务中写入；Agent 不能用这些操作跳过执行、评审或确认停止。

### 数据流与控制流意图

- 取消：预览当前依赖图 → 展示影响和运行 → 显式停止并确认 → 绑定版本/哈希提交 → 事务更新任务、需求与验收 → SSE 刷新。
- 归档：已结束任务 → 确认收起 → 日常视图过滤 → 历史查询/详情保留 → 显式恢复可见性。

### 破坏面清单

- `refreshSource`：含取消工作的计划不能进入最终验收，需求保持需处理。
- 计划批准/修订：已取消需求不可再进入执行或规划。
- SQLite 列表过滤、HTTP 查询与看板：仅日常视图过滤归档；证据关系和内部调度读取保留完整记录。
- 共用任务/运行抽屉与计划/验收面板：显式传递所属项目，只读访问不切换或恢复归档项目。
- 原有人工续租、Agent 协议、拖动与最终验收：保留运行绑定、文件锁和证据校验。

### 复杂度预算与裁决

新增两个用户概念：取消业务工作、收起/恢复历史记录；它们分别改变执行意图和可见性，不能合并。归档批次只是父子恢复关系，不新增用户配置。结构放行，沿用现有模块和事务，不增加服务层级。
