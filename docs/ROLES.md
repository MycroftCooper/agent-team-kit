# Roles and write scopes

A role is three things: an **id** in the config, a **set of path prefixes** in
`ownership.json`, and a **card** in `<flowDir>/roles/<ROLE>.md`. The CLI enforces
the middle one; humans and agents read the card.

## Define roles

1. List them in `agent-flow.config.json`:

   ```jsonc
   "roles": ["LEAD", "FE", "BE", "QA"]
   ```

   IDs are upper-case (`^[A-Z][A-Z0-9_]*$`), unique, and their order is the
   display order on the board.

2. Regenerate cards (or add them by hand):

   ```bash
   atk init --roles LEAD,FE,BE,QA --force
   ```

   `atk init` writes a card for every role: a specific bundled card for
   `LEAD`/`DEV`/`FE`/`BE`/`QA`, and a generic card for anything else. `--force`
   overwrites generated files, so customize cards after the last `init`.

3. Map paths to roles in `ownership.json` (next section).

## Write scopes: `ownership.json`

```jsonc
{
  "schemaVersion": 1,
  "roles": ["LEAD", "FE", "BE", "QA"],
  "ignoredPrefixes": ["artifacts/", "node_modules/", ".git/", "dist/"],
  "rules": [
    { "prefix": "tests/qa/", "role": "QA", "note": "acceptance tests" },
    { "prefix": "src-tauri/", "role": "BE", "note": "host / backend" },
    { "prefix": "src/", "role": "FE", "note": "frontend code and tests" },
    { "prefix": "docs/", "role": "LEAD", "note": "documentation" },
    { "prefix": ".agent-flow/", "role": "LEAD", "note": "workflow state" }
  ],
  "rootFiles": { "role": "LEAD", "names": ["package.json", "tsconfig.json"] }
}
```

Rules:

- **Longest prefix wins.** `tests/qa/` beats `tests/`, `src/` beats the root.
- A path may be claimed by **one** role. Two roles on one path is a config error;
  `atk ownership verify-config` reports it.
- Prefixes are compared as project-relative posix paths and are usually written
  with a trailing `/`.
- `ignoredPrefixes` are never checked (build output, caches, artifacts).
- `rootFiles.names` are root-level config files owned by one role.

Scope lives in the config, not in the role card: the card explains the intent,
the config decides. When they disagree, the config wins — fix the card.

## Check a scope

```bash
atk ownership map src/features/a.ts        # which role owns this path
atk ownership check --role FE --files a.ts,b.tsx
atk ownership check --role FE               # changed files vs git working tree
atk ownership verify-config                 # conflicts + unused roles
```

`atk ownership check` exits `1` on a violation, so it works as a preflight gate
step (the bundled `p4deck` preset wires it into `atk gate fast`). An agent that
needs a file outside its scope stops and messages LEAD; it does not edit and
explain afterwards.

## What a role card contains

Every card generated by `atk init` carries the same contract:

- **Write scope** - the paths, and how to verify them.
- **Do not** - the forbidden actions for that role (plus QA's iron rules).
- **Task loop** - the ordered steps from ticket to receipt.
- **Receipt format** - exactly 6 lines: scope / commands / tests / blockers /
  snapshot / stop.
- **Commands** - the `atk` commands the role actually needs.
- **Round budget** - `<= 12` rounds per task (`<= 10` for a QA slice).
- **Proof ladder** - `typecheck ok` is not `tests passed`, and `tests passed` is
  not `human-accepted`.

## Adding a role

Example: a designer role that owns `design/` and nothing else.

```jsonc
// config
"roles": ["LEAD", "DESIGN", "DEV", "QA"]

// ownership.json
"rules": [
  { "prefix": "design/", "role": "DESIGN", "note": "design tokens and specs" },
  { "prefix": "src/", "role": "DEV", "note": "product code" }
]
```

Then:

```bash
atk init --roles LEAD,DESIGN,DEV,QA --force     # writes roles/DESIGN.md (generic card)
atk ownership verify-config                     # no unused roles, no conflicts
atk queue --for DESIGN
```

The generic card is a starting point; edit `roles/DESIGN.md` to add the role's
real task loop and receipt examples. Do not put scope in the card — put it in
`ownership.json`.

## Role sets that work well

| Set | Use when |
|---|---|
| `LEAD, DEV, QA` | small projects, one implementation role |
| `LEAD, FE, BE, QA` | separate frontend and host/backend, one integrator |
| `LEAD, DEV, QA, REVIEW` | you want a review step distinct from QA; give REVIEW no product write scope |

A role without any write scope is valid (e.g. an observer or reviewer); assign it
only root files or no paths at all.
