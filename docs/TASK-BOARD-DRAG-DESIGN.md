# 任务看板拖动设计

状态：第一版已实现。核对日期：2026-11-14。

## 交互原则

拖动触发现有的人类业务操作。目标列只表达操作完成后的结果，最终状态由后端根据任务、计划、运行、证据和锁共同决定。前端不提供任意写入 `status` 的接口。

卡片分为需求、人工工作、Agent 工作。不能只按卡片当前所在列判断可放位置。

当前真实列定义：

- 预排：`DRAFT`。
- 待开始：`READY`，也包括仍在等依赖或文件锁的任务。
- 进行中：`RUNNING`。
- 待评审：`REVIEWING`。
- 待验收：`VERIFIED` 的工作子任务与 `AWAITING_ACCEPTANCE` 的需求。
- 需处理：`BLOCKED`。
- 已结束：`DONE`、`CANCELLED`。

“等待”“联系过期”“已请求停止”分别是调度、联系或 Run 的情况，不新增同名 Task 状态。`CANCELLED` 的现有来源包括计划修订取消旧任务；当前没有通用的人类取消/重开任务 API。

## 第一版开放的拖动

### 1. 人工工作：待开始 → 进行中

- 对应操作：开始人工任务。
- 条件：当前计划已批准、前置工作完成、项目可用、完整文件范围可取得锁、任务版本未变。
- 放下后：直接执行现有 `POST /tasks/:id/human-start`，成功后移卡。
- 后端会建立真实 HUMAN Run、租约和必要文件锁；工作台继续跨页面续租。
- 有未完成依赖或文件占用时，目标列不开放，并显示具体原因。

### 2. 人工工作：进行中 → 已结束

- 对应操作：提交人工交付。
- 放下后：打开已有交付表单，填写完成说明和计划要求的检查结果。
- 提交成功：该人工任务 `RUNNING → DONE`，不是 `VERIFIED`；所属需求是否进入待验收由全部子任务的实际状态决定。
- 取消、缺少证据或运行失效：卡片留在原位。
- 不开放“待开始直接拖到已结束”，因为当前业务需要先创建并执行 HUMAN Run。

### 3. 工作任务：需处理 → 待开始

- 对应操作：重新排队，复用 `POST /tasks/:id/retry`。
- 条件：任务确实 `BLOCKED`，计划仍获批准，没有活动或不确定 Run；沿用现有重试接口的权限和项目约束。
- 放下后：确认重新排队，随后显示后端的当前等待原因。
- 重新排队只恢复领取资格；依赖或锁尚未满足时，任务仍可留在 `READY` 等待，并不承诺立即执行。
- 若旧运行 `RUNNING`、`STOP_REQUESTED` 或 `QUARANTINED`，禁用目标并引导先在详情中处理停止；不能把一次拖动视为已确认外部进程停止。
- 人工工作和 Agent 工作都可在符合相同业务条件时重试。

### 4. 需求：预排 → 待开始

- 对应操作：批准已经提交的计划版本。
- 条件：需求仍指向当前 `SUBMITTED` 计划；只有 DRAFT、没有已提交计划时不开放此目标。
- 放下后：打开现有计划详情，展示分工、依赖、文件范围、检查和验收，用户点击批准。
- 批准成功：需求进入 `READY`，同时由后端物化子任务；不能只移动需求外观而漏掉子任务。
- 旧版本、规划尚未提交、计划变动或执行占用等情况按现有 `approvePlan` 校验拒绝。

### 5. 需求：待验收 → 已结束

- 对应操作：确认整份计划验收通过，复用现有最终验收页面与接口。
- 条件：需求确实 `AWAITING_ACCEPTANCE`，当前计划/验收目标匹配，全部子任务已 `VERIFIED` 或 `DONE`，产物和当前文件一致且无冲突锁。
- 放下后：打开验收面板，明确展示整项需求、证据及将同时关闭的已验证子任务。
- 确认成功：需求和对应已验证子任务同步变为 `DONE`。证据失效时留在原位并提示重验。
- 同列里的 `VERIFIED` Agent 子任务不能单独拖到已结束；其关闭属于整项需求的最终验收。卡片提供“查看所属需求验收”入口。

## 保留为详情操作的人工动作

- 要求修改计划：现有 `POST /plans/:id/revise` 会将需求退回 `DRAFT`，取消未完成的旧子任务并使旧验收失效；当前计划不得有活动或不确定运行。第一版保留原有修改原因与影响确认入口，不开放“向左随意拖回预排”。
- 请求停止、确认停止：操作对象是 Run。请求停止不会立刻把 Task 移到需处理；确认外部写入已停后才释放锁并由后端变更任务。需要保留 Run 详情。
- 指派、改派：更改执行资格，不改变任务状态。沿用卡片及详情中的指派操作。
- 产物变化后的重验：由现有验收重验流程处理，不能把卡片拖回待评审来制造一次评审。

## 不开放人工拖动的转换

- Agent 工作的待开始 → 进行中：实际 Agent 领取后进入。
- Agent 工作的进行中 → 待评审/待验收/已结束：由停止写入后的真实交付回执和评审策略决定。
- 待评审 → 待验收：由独立评审 `PASS` 决定；人类在页面上不能冒用 REVIEWER 身份通过评审。
- 待评审 → 待开始：由评审的 `CHANGES_REQUESTED` 决定；人类调整方案应走需求级计划修订。
- 进行中 → 需处理：失败、漂移、租约过期、停止确认等各有业务原因，不是通用“暂停”。
- 已结束 → 任意列：当前没有直接重开 API；后续如增加撤销、取消、重开，应单独设计生命周期与回执规则。
- 同列重新排序：当前看板按优先级、时间等规则排序；第一版的拖动只表达状态操作，不增加手工排序字段。

## Bug 的范围

当前任务看板在后端排除了 `BUG`，Bug 单使用独立列表。第一版不把 Bug 隐式并入任务看板。

将来给 Bug 单增加看板时，可复用相同交互：

- 待验收 → 已关闭：打开 Bug 修复验收，校验当前 `version`、`resultHash`、文件与锁。
- 待验收 → 待修复：填写退回原因，再调用 `reviewBug(REJECT)`。
- 已阻塞 → 待修复：无活动或不确定运行后重试。
- 待修复 → 修复中、修复中 → 待验收仍由修复 Agent 的领取与交付决定。

## 看板操作细节

1. 卡片保留点击名称打开共用右侧详情抽屉；拖动从独立把柄开始，设置约 6–8 像素的激活距离，避免误触。
2. 开始拖动时只高亮当前卡片可执行的目标，直接写“开始人工任务”“填写交付后完成”“审核并批准计划”等动作名称。
3. 不可放目标给出具体原因，不只显示禁用光标。没有可用动作的卡片不提供可用拖动把柄，并保留详情入口。
4. 需要补充信息、批准或验收时，放下只打开对应业务表单/详情；原卡片保留，目标位置可显示“待确认”。取消后收起，保留筛选与滚动位置。
5. 确认并收到后端成功回执后再移卡；失败展示实际原因并刷新最新状态，不先假定完成后回滚整列。
6. 提交期间只禁用本卡片的重复操作。SSE 并发更新了该任务、计划或验收目标时，取消旧拖动/提示重新核对；不覆盖新结果。
7. 第一版只支持单张卡片。状态看板与状态列泳道可以使用；泳道只在当前任务类型内横向移动。
8. 按类型分组的“需求/人工/Agent”不是状态目标；跨类型拖动不得更改 executorType。隐藏列不成为不可见落点。
9. 非拖动入口保留现有按钮，并提供同一组“移动到…”动作；键盘、触屏无需拖动也可完成业务操作。Esc 取消拖动、选择或待确认操作。
10. 完成后若卡片不再符合当前筛选，提示“操作成功，任务已移出当前筛选”，不将消失误报为失败。

## 最小实现结构

新增一个“可执行人类动作”的投影，描述动作、目标列、交互方式、是否可用和具体原因；按钮和拖动共同使用它。状态列只负责展示，不推导权限。

建议动作：`START_HUMAN`、`COMPLETE_HUMAN`、`RETRY_TASK`、`APPROVE_PLAN`、`ACCEPT_PLAN`。交互方式为直接操作、交付表单、计划审核、最终验收或确认。

后端根据任务类型/状态、计划与验收摘要、依赖、活动 Run、锁和项目情况计算投影；列表/看板只返回轻量摘要，不预取产物、完整日志或所有计划细节。便宜的可用性预检不能替代实际业务接口内的原子校验。

前端将动作分发到现有的业务接口，不新增通用的 `PATCH status` 接口。提交绑定当前任务/计划/验收版本与目标哈希；需要填写表单时，临近提交再次核对。

人工交付已补齐运行绑定：`finishHuman(taskId, body)` 要求 `version`、`runId`、`generation`，在同一事务中校验任务和活动 HUMAN Run。所有人工交付入口使用相同面板；旧表单不会误完成一次后来重启的新运行。表单因并发更新失效时保留输入并禁止提交，用户可重新打开核对。

受影响范围：`BoardTaskCard`/状态看板/泳道、共用详情与业务表单、任务投影、人工交付提交校验。现有按钮、直接链接、筛选/分页、SSE、工作台人工续租、独立评审与锁机制均须保留。

## 验收重点

- 五类允许操作各走实际接口；没有计划的预排需求、未满足依赖的人工任务、带旧 Run 的重试等禁用并有原因。
- 人工任务确实创建 Run，交付确实生成回执；不能用直接改状态替代。
- 计划批准实际生成子任务；最终验收确实关闭相关子任务并绑定当前目标。
- Agent 领取、执行交付、独立评审的转换不被拖动绕过。
- 拖到同列、错误列、不同类型泳道、隐藏列、已有终态卡片均不产生错误写入。
- 取消表单、提交失败、并发 SSE、版本冲突、产物漂移、停止未确认、过期人工表单都保持真实状态。
- 点击开抽屉、拖动把柄、键盘等价动作、窄屏和项目切换不互相干扰。

## 实现与验证入口

- `apps/backend/src/task-actions.mjs`：五类人类动作的轻量可用性投影；实际业务接口仍做最终校验。
- `apps/web/src/task-actions.ts`、`task-movement.tsx`：共享动作语义、7 像素指针激活、可见列落点、边缘横向滚动、Esc、并发取消与“移动到…”等价入口。
- 人工交付、重试、计划批准、最终验收保留业务面板；确认完成后才刷新卡片位置。只有开始人工任务直接执行。
- `node scripts/task-movement-e2e.mjs`：使用隔离项目、真实浏览器指针与 HTTP，验证五类转换、取消、旧表单、SSE 并发、泳道执行类型边界和窄屏筛选。证据保存在 `artifacts/task-movement-e2e`。
