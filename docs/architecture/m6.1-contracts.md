## 1. F01 — Task 状态迁移权限

**通用 `PATCH /api/v1/tasks/:id` 只允许这些目标状态**：

| 目标 | 条件 |
|---|---|
| `READY` | 仅当当前为 `DRAFT`、`REJECTED`（返工重排）、`BLOCKED`（解除阻塞） |
| `BLOCKED` | 任何非终态 |
| `CANCELLED` | 任何非终态 |
| 同状态 | 视为 no-op（幂等 200） |

**执行态一律拒绝**（`CLAIMED`/`RUNNING`/`REVIEWING`/`INTEGRATING`/`AWAITING_ACCEPTANCE`/`DONE`）：
`409 TASK_VERSION_CONFLICT`，`details = { taskId, requestedStatus, reason: "execution-state-guard", allowedTransitions: [...] }`。

**专用入口（唯一合法路径）**：

| 迁移 | 入口 | 前置条件 |
|---|---|---|
| `READY → CLAIMED` | `POST /internal/v1/tasks/:id/claim`（Scheduler，`x-atk-internal-role: scheduler`） | 依赖 DONE、容量、写域、CAS（已有） |
| `CLAIMED → RUNNING` | `POST /internal/v1/runs/:id/events` 中的 `session.started`（role `runtime-host`） | 有效租约 + generation |
| `RUNNING → COMPLETED/FAILED/INTERRUPTED` | 同一 events 批次里的 `session.ended` | 同上 |
| `RUNNING/COMPLETED → REVIEWING` | `POST /api/v1/reviews`（创建 review） | 任务必须有**该 task 的 COMPLETED Run**；进入 REVIEWING 与创建 review 同事务 |
| `REVIEWING → INTEGRATING` | `submitReview(PASS)` | 证据齐全（已有） |
| `REVIEWING → REJECTED` | `submitReview(CHANGES_REQUESTED)` | findings 非空（已有） |
| `INTEGRATING → AWAITING_ACCEPTANCE` | `POST /internal/v1/tasks/:id/integration`（role `scheduler` 或 `user-action`） | **必须有集成记录**：`{ taskId, runId, commitSha, manifestHash }`，且 `manifestHash` 等于 `tasks.target_hash` |
| `AWAITING_ACCEPTANCE → DONE` | `POST /api/v1/approvals/:id/decide`（human） | APPROVED + targetHash 一致（已有） |
| `AWAITING_ACCEPTANCE → READY` | 同上 REJECTED（已有） | |

store 层同样拒绝通用 patch 推进执行态（双层防护，WP2 实现）。

## 2. F06 — 身份与授权边界

**不再信任请求体里的 `actor`**（保留字段仅为向后兼容日志，服务端一律忽略）。

- **Review 身份**：`createReview` 必须携带 `reviewerAgentId`，由**内部 API**（role `scheduler` 或 `user-action`）创建；一个 review 即一条 assignment：`{ reviewId, taskId, reviewerAgentId, createdByRole }`。
- `submitReview` 必须由 **runtime-host 内部凭据**提交，且批次所属 Run 的 `agentId` 必须等于该 review 的 `reviewerAgentId`；否则 `403 NOT_AUTHORIZED`，`details.reason = "review-assignment-required"`。
- 自审判定改为：`review.reviewerAgentId === 被评审 Run 的 agentId` → `403 SELF_REVIEW_FORBIDDEN`。
- **Human Approval**：走浏览器会话（session token + CSRF），`actor` 由服务端填 `"HUMAN"`；请求体里的 `actor` 被忽略；审计事件 `approval.recorded` 带 `{ principal: "HUMAN", operation, targetVersion, targetHash, at }`。
- **内部凭据角色分离**：header `x-atk-internal-role: scheduler | runtime-host | user-action`；每个内部端点声明允许的角色，缺失/不匹配 → `403 NOT_AUTHORIZED`，`details.reason = "internal-role-required" | "internal-role-forbidden"`；现有 `x-atk-internal` 继续作为凭据本身（角色是附加断言）。
- Agent 子进程**不继承** session token（Launcher 只传内部凭据，且 runtime-host 角色不可调用 claim/approval）。

## 3. F02 — 完成回执的确认语义

- `POST /internal/v1/dispatch/:id/result` 成功响应必须含 `{ persisted: true, run, command }`。
- 同 generation 重放 → 同一结果 200（`persisted:true`），**不产生第二条 `run.updated`**。
- store 写入失败（非 `STALE_GENERATION`）→ **5xx**（Host 保留 Outbox 重试）；只有租约/generation 问题返回 409。
- Host 侧新增本地 `FINISHING` 状态与持久 Outbox：`{ runId, commandId, ownerId, generation, eventId, payload, attempts, lastError, nextAttemptAt }`，原子写（tmp+fsync+rename），Backend 确认后才删除。
- 对账：`GET /internal/v1/runs/:id/reconcile` 返回 `{ run, lease, sessions, pendingResult? }`；Host 用它判断"请求已提交但响应丢失"。

## 4. F03 — 批次事务

```js
applyRuntimeEventBatch({ runId, generation, events, now })
  -> { ok: true, run, applied: Event[], skipped: number, duplicate: number, stateChanged: boolean }
```

**`events[]` 元素形状（冻结，方案 A）**：route 负责 runtime 语义（`session.started/ended` → Run 状态），store 只接收**已映射事件**：

```js
{ type: "run.updated", payload: { status, exitCode?, endedAt? }, eventId?, sessionSeq? }
{ type: "run.log",     payload: { ... },                      eventId?, sessionSeq?, legacy? }
```
- store 对 `run.updated` 执行状态机迁移并写该条事件；对 `run.log` 只写事件。全部在同一事务。
- 批次中**允许多条** `run.updated`（真实 Host 会把 `session.started` 与 `session.ended` 一起刷出，route 映射后就是多条迁移）：store **按顺序**对当前状态逐条校验并应用，任一条非法 → `VALIDATION_ERROR`（`details.index`），整个批次回滚。**禁止**跳步（如 STARTING→COMPLETED 未经 RUNNING）。空批次 = 纯 fence（校验 generation，写 0 条）。
- `eventId` / `sessionSeq` / `legacy` 持久化在**事件行顶层**。
- `reconcileRun` 可选返回 `pendingResult: { commandId, generation, status: "DONE"|"FAILED", result }`，由 store 产生，route 只透传（不自行推导）。
- **单事务**：先全量校验（类型/字段/事件下标）→ generation+租约校验 → 逐条去重 → Run 状态迁移 → 写事件；任一步失败整体回滚，返回 `{ ok:false, problem:{ code, index?, field? } }`。
- 去重不报错：重复事件计入 `duplicate` 并跳过；未知类型/字段 → 400（`details.index` 指出第几条）。
- `STALE_GENERATION` → 409，零写入。
- memory 实现用快照回滚，行为与 SQLite 一致。

## 5. F08 — 事件身份

- 事件字段：`eventId: string`（Host 生成，稳定，重试复用），`sessionSeq: integer`（每个 session 单调递增）。
- 去重键：`eventDedupeKey(event)`（`@atk/contracts`）——有 `eventId` 用 `id:<eventId>`，否则回退旧的复合键（仅兼容历史事件）。
- 持久唯一约束：`(run_id, event_id)`；migration `0006_event_ids.sql`，schemaVersion → 6。
- 旧事件（无 eventId）允许写入，标记 `legacy: true`，不参与新键去重。
- 同一事件重复提交 3 次 → 只有 1 条；同一毫秒 100 条不同 eventId → 全部保留。

## 6. F11 — Review 分页

- store：`listReviews({ taskId?, status?, limit, cursor? })` → `{ items, hasMore, nextCursor? }`；**先过滤、后排序分页**；keyset 分页，`nextCursor` 为不透明字符串（`<createdAt>|<id>` 编码）。
- HTTP：`GET /api/v1/reviews?taskId=&status=&limit=&cursor=` → `{ items, hasMore, nextCursor? }`；`total` 仅在 `withTotal=1` 时返回（默认省略，避免全表 count）。
- memory 与 sqlite 结果必须逐字段一致。
